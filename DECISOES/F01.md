1. Eu não tenho nenhum conhecimento prévio do que está sendo pedido, literalmente. Não tenho experiência com back end. Conheço abortController e Promises e nada mais.
2. Minha questão aqui é puramente conceitual, primeira vez que implemento uma camada de rede resiliente do zero; registrei os trade-offs aqui para conseguir defender cada escolha. A não utilização de uma lib é para compreender os conceitos postos nesse custom httpClient.
3. Agora pretendo implementar com ajuda, buscando entender cada conceito e detalhe e tentar descobrir outras formas que poderiam ser feitas, na tentativa de gerar um conhecimento mais amplo do que essa fase pede.
4. iniciando a separação do que é cliente e servidor um projeto para o front end bazar-front e um novo para a api e chamarei de bazar-mock-server que funcionará como auxiliar para testes de requisições do front end.
5. utilizando Hono, por facilidade de setup, performance satisfatória para o cenário atual e pelo suporte nativo ao typescript e utiliza web-api modernas (request, response, fetch).
6. bazar-mock-server api falsa com um gerador pseudo-aleatório (PRNG) com seed fixa, para os ids de itens do servidor terem sempre o mesmo identificador, mesmo após encerrando de runtime.
7. Latência aleatória (rtt) controlada entre 80 e 1200ms, erros sem resposta (sem retorno) serão na casa 2% e 8% gerarão erros de servidor para gerar os cenários de erro, como foi solicitado na f01 da camada de rede.
8. O server tem uma paginação baseada em cursor, para consistência visual dos dados apresentados, funciona como um marcador de página, ele não perderá referência de informação mesmo que alguma informação seja apagada, ao contrário do offset que utiliza a posição de página específica e tendo que varrer outras anteriores se existir. Offset funciona como uma contagem sequencial e cursor como uma busca indexada e imutável no tempo.
9. custom httpClient para aprofundar no entendimento conceitual e prático de idempotência onde requests de gravação e criação precisam de uma avaliação mais criteriosa no momento de retry cego, para não gerar duplicação/sobrescrita indesejada de registros.
10. Controle de fila com concorrência limitada em 6 e ordenação por prioridade, em caso de prioridade igual FIFO original, sempre mantendo processamento ativo verificando slots vazios.
11. Implementação de recuo exponencial com jitter para evitar sobrecarga e quedas em cascata durante falhas transitórias do servidor.
12. Deduplicação para eliminar cópias repetidas de requests. Um deduplicador de requisições em voo gerencia concorrência momentânea, não persistência; esquecer de limpar a chave no finally transforma a otimização de rede em um cache quebrado que serve dados congelados para sempre.
13. Uso de promise para gerenciar como os dados serão retornados, com tempo limite, em lotes de forma isolada para cada promise e garantir comportamento individual disparando erros se ultrapasar limite estipulado e não cancelar as que derem sucesso. AllSettled para manter os sucessos apesar de erros e race como cronômetro para as promises reais serem encerrados em tempo determinado.
